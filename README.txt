SkillPath - система мониторинга развития технических навыков
Решение кейса №4 "Я хочу развиваться"

Сайт: https://skillpath.duckdns.org/
Репозиторий: https://github.com/Aludra568/skillpath


ЧТО ЭТО

Система для руководителя команды разработки, чтобы вести обучение сотрудников
в одном месте, а не в таблицах, заметках и чатах.

Что умеет:
- годовой план обучения: скиллы из справочника и дата, к которой скилл надо
  подтвердить
- протоколы встреч один на один: итоги текстом, ссылки, отметки по скиллам,
  фиксация проблем
- прогресс считается сам: отметили скилл зачтённым на встрече - он поменял
  статус в плане и попал в статистику отдела
- аналитика по подразделению и по каждому сотруднику
- список сотрудников с фильтрами по направлению и подразделению
- структура подразделений в виде дерева любой глубины
- календарь встреч и сроков подтверждения скиллов

Смысл в том, что руководитель не заполняет отчётность отдельно. Он ведёт
протокол встречи, а прогресс, просрочки и аналитика считаются из него.


ОСНОВНОЙ СЦЕНАРИЙ

1. Первый человек регистрируется и становится владельцем компании
   (администратором). Остальные регистрируются сами, администратор добавляет
   их в нужное подразделение.
2. Администратор заводит направления (BACK, FRONT, QA) и скиллы, строит
   структуру подразделений, назначает руководителей.
3. Руководитель открывает карточку сотрудника и добавляет скилл в план
   обучения с плановой датой.
4. Назначает встречу. В протоколе пишет итоги, добавляет ссылки.
5. Отмечает скилл зачтённым - статус в плане меняется автоматически.
6. Если есть проблема, фиксирует её по скиллу или по сотруднику.
7. Возвращается в карточку: процент выполнения вырос, на главной
   пересчиталась сводка по отделу.


КАК УСТРОЕНЫ ПРАВА

Главное требование кейса: роль зависит не от пользователя, а от того, чей
профиль он открыл. Поэтому глобальных ролей "руководитель" и "сотрудник" у
нас нет. На каждый запрос считается отношение между двумя людьми:

  admin   - администратор, видит всё
  manager - открывший выше по дереву, может вести PR: план, встречи, зачёты
  self    - свой профиль, только просмотр
  none    - чужая ветка, доступ запрещён

Всё строится на дереве подразделений: руководитель узла ведёт всех, кто есть
в этом узле и во всех вложенных, на любую глубину. Из этого само собой
получается, что один и тот же человек одновременно руководитель для своих
подчинённых и подчинённый для вышестоящего. Если перенести сотрудника в
другое подразделение, права переезжают вместе с ним.

Права проверяет сервер, каждый метод API вызывает проверку. Кнопки в
интерфейсе ничего не защищают, они просто не показывают лишнее.


ЧТО СДЕЛАНО ПО ПУНКТАМ КЕЙСА

Пользователи. Регистрация, вход по почте и паролю. Профиль: ФИО, должность,
направление, подразделение, руководитель. Администратор может добавлять,
изменять и удалять пользователей.

Структура подразделений. Дерево любой вложенности, у каждого узла свой
руководитель. Подразделение и сотрудника можно перенести в другой узел, при
переносе проверяется, что не получится цикл.

Авторизация. Администратор видит всё, руководитель - своё поддерево в виде
дерева, сотрудник без подчинённых - только себя.

Встречи. Протокол содержит дату, участника и того, кто проводит, итоги с
разметкой markdown, ссылки, отметки по скиллам (обсуждали / зачтён) и
проблемы с комментарием.

Скиллы. Справочник сгруппирован по направлениям, редактирует администратор.
Скилл, который уже стоит у кого-то в плане, удалить нельзя, чтобы не ломать
историю встреч.

Аналитика. По подразделению: процент выполнения плана, число сотрудников,
просрочки, открытые проблемы, проведённые встречи, список тех, кто требует
внимания. Вложенные подразделения считаются вместе с родителем. По
сотруднику: что зачтено, что просрочено, открытые проблемы, ближайшая
встреча.


ДОПОЛНИТЕЛЬНАЯ ВОЗМОЖНОСТЬ

Кейс советует взять один-два пункта и довести до рабочего состояния. Мы взяли
один - календарь PR-встреч. Месячная сетка, в которой вместе показаны встречи
и плановые даты подтверждения скиллов. Сразу видно, где срок по скиллу
наступает раньше, чем следующая встреча. Клик по событию открывает протокол
или карточку сотрудника. На главной те же события идут короткой лентой.


ТЕХНОЛОГИИ

Бэкенд: Python, FastAPI, SQLAlchemy, SQLite, JWT для токенов
Фронтенд: React, TypeScript, Vite, marked + DOMPurify для markdown
Деплой: Docker, один контейнер отдаёт и API, и собранный фронтенд


КАК ЗАПУСТИТЬ

Через Docker:

    docker compose up --build

Открыть http://localhost:8000, документация API - /docs

Без Docker:

    python -m venv .venv
    .venv/Scripts/activate
    pip install -r backend/requirements.txt
    cd frontend
    npm install
    npm run build
    cd ../backend
    python -m uvicorn app.main:app --port 8000

База создаётся сама при первом запуске в папке data. Она пустая: первый, кто
зарегистрируется, станет администратором. Чтобы начать с нуля, удалите папку
data.

Если забыли пароль или нужен второй администратор, есть команды (запускать из
папки backend):

    PYTHONPATH=. python manage.py users
    PYTHONPATH=. python manage.py make-admin почта@компания.ru
    PYTHONPATH=. python manage.py set-password почта@компания.ru новыйпароль


ТЕСТЫ

    cd backend
    PYTHONPATH=. python tests/test_app.py

15 тестов. Компания в них собирается через API теми же шагами, что и живым
администратором: регистрация владельца, справочник, дерево подразделений,
распределение сотрудников. Проверяем регистрацию (первый становится админом,
остальные без подразделения, дубль почты, короткий пароль, смена пароля),
полный цикл план - встреча - зачёт - прогресс и откат зачёта, видимость
только своего поддерева, недоступность чужого сотрудника, запрет цикла при
переносе подразделения, доступ к справочнику только у администратора, фильтры
и события календаря.


ОГРАНИЧЕНИЯ MVP

1. База SQLite. Для демо хватает, для продакшена нужен PostgreSQL и миграции,
   сейчас схема создаётся автоматически при старте.
2. Права считаются запросом в базу на каждый вызов, без кеша. На тысячах
   сотрудников это надо будет оптимизировать.
3. К встрече можно приложить только ссылку, загрузку файлов не делали.
4. Регистрация открытая. Кто угодно может зарегистрироваться по ссылке, но
   пока администратор не добавил его в подразделение, он видит только себя.
   Приглашений по почте и восстановления пароля нет, пароль меняет сам
   пользователь или администратор.
5. Время хранится в UTC, показывается в часовом поясе браузера.
6. План один на сотрудника в год, незачтённые скиллы переносятся вручную.
7. Уведомления в мессенджер и геймификацию не делали, взяли только календарь.


ИСПОЛЬЗОВАНИЕ ИИ

Использовали Claude (Anthropic). Где применяли: генерация и рефакторинг кода
бэкенда и фронтенда, вёрстка экранов, черновики тестов и документации.

Всё проверяли запуском: тесты проходят, фронтенд собирается в строгом режиме
TypeScript, основной сценарий прогоняли в браузере руками.
